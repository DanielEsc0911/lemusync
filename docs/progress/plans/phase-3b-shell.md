# Phase 3b, app shell and live status

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Also follow the project skills: `lemusync-feature` (always), `lemusync-docs` (every task), `lemusync-ui` (Tasks 5–9), `lemusync-security` (Tasks 3, 4: IPC client, data from the socket).

**Goal:** The LemuSync desktop app opens, finds the running daemon, and shows what it knows: a five-destination shell (same order everywhere, F3), a Home with the live status hero and the play-session overlay, recent games, and a read-only Games library, all fed by the daemon's event stream through the bridge. Second of the four Phase 3 plans ([roadmap](../roadmap.md#phase-3-flutter-app-desktop), [D40](../../decisions.md#d40-the-desktop-ui-comes-before-the-windows-and-macos-daemon-2026-11-01)). Linux first; the code has no per-OS visual branch.

**Architecture:** The app is a client of `lemusyncd` ([D35](../../decisions.md#d35-the-cli-is-the-daemons-client-while-it-runs-2026-10-28)): Flutter → FRB → `crates/bridge` → `crates/ipc` `Client` → the daemon socket. `lemusync_ipc::Client` already is the shared client (the CLI's `daemon_client.rs` wraps it with CLI-only typing), so nothing moves down a layer and no protocol is added. The bridge gets a `link` module (plain async Rust, tested against a real `lemusync_ipc::Server`) and a thin `api/daemon.rs` FRB surface over bridge-owned DTOs (no serde, no secrets). Calls use one short connection each; one long-lived task owns the event subscription (the daemon's `Subscribe` loop never reads requests again, so a subscribed connection cannot also call: `crates/daemon/src/run.rs`) and reconnects with backoff. "Daemon not running" is a value (`ConnectionState`), never an exception. The game-library rule (which games, in which order, launchable or not) is one pure function in `lemusync-api` shared by the tray and the app. In Dart, one `AppController` (a `ChangeNotifier`, no new package) holds connection, status, session, library and live transfers, built from the event stream and tested with a fake link. `AppShell` shows the destinations as bottom bar, rail or sidebar by width.

**Tech Stack:** Rust 1.99.0; existing workspace crates `tokio`, `futures-util` (already in `Cargo.lock`, now also `lemusync-bridge` dependencies) plus `lemusync-api` and `lemusync-ipc` (allowed for `bridge` by `cargo xtask layers`); `flutter_rust_bridge` Rust `=2.13.0`, Dart `2.13.0`, codegen 2.13.0 (pinned in `app/pubspec.yaml` and `crates/bridge/Cargo.toml`; `flutter_rust_bridge_codegen --version` printed 2.13.0 on 2026-11-01); Flutter 3.47.6. No new Dart or Rust package (router and state use the framework: P1).

**Spec:** [navigation](../../specs/ui/navigation.md) §Destinations, §Adaptive containers, §Deep links, §Desktop extras; [design-system](../../specs/ui/design-system.md) §Components, §Accessibility, §Performance; [status-and-notifications](../../specs/ui/status-and-notifications.md) §Status model, §Desktop tray and menu bar; [architecture](../../specs/architecture.md) §Components, §Engine API, §IPC, §Bridge; `app-shell` (new, Task 1: `docs/specs/ui/app-shell.md`, linked once it exists); [testing](../../specs/testing.md) §Layers, §Rules; [i18n](../../specs/i18n.md) §Terminology. - **Decision for the maintainer (F2, F3): unbuilt destinations are honest placeholders.** Activity, Devices and Settings come in 3d. All five destinations are in the shell from 3b, in spec order, so navigation never changes later (F3). The three unbuilt ones show an `EmptyState` that says what will appear there and gives the CLI equivalent as selectable text (P5): Activity → `lemusync history <game>`, Devices → `lemusync status`, Settings → `lemusync config list`. No button, no switch, nothing tappable that does nothing. Alternative rejected: hiding them until 3d (the rail would reorder later; F3). The maintainer may veto this in the Task 6 review.
- **Decision for the maintainer: Play stays out of 3b.** Play needs the lease and conflict prompts (`PlayQuestion`), which are 3c flows ([navigation §Play](../../specs/ui/navigation.md#play-launcher-mode)). 3b is read-only except one write the daemon already treats as its own: **Sync now** (`Request::Sync { dry_run: false }`, the tray's and Ctrl+R's action). `GameCard` shows no Play button when `onPlay` is null (a small change to the 3a component, Task 8); the tray keeps launching games meanwhile.
- **No router package.** `pubspec.yaml` has no `go_router`; the shell needs one flat set of five destinations, with detail views arriving in 3c. A `Destination` enum, one `ValueNotifier<Destination>` and an `IndexedStack`-free single body (only the active screen is built, so hidden screens cost nothing) is enough (P1). Deep links (`lemusync://`, navigation §Deep links) come with notifications in 3d and will map onto the same enum.
- **The app never runs an engine on desktop** (D35: one engine per profile holds the state lock). Without a daemon the app shows the offline state; it does not start or stop the daemon (that is `lemusync service start`, P5).
- **No secrets cross the bridge.** The DTOs carry names, ids, counts, times and paths the daemon already shows in `status` and `games`; no `Secret`, no passphrase, no tokens. Paths in `GameInfo.path` stay in Rust: Dart gets `launchable: bool` only (B2; it is also all 3b needs).
- **B3 for the UI:** reconnect never spins: backoff 1 s doubling to 30 s, reset on success; a stopped listener (Dart cancelled the stream) ends the task. No polling while connected (idle budget): the snapshot is refreshed on connect, on app resume and on `Lagged` recovery (below), not on a timer. Window close quits the app only; the daemon, the tray and the sync keep running.
- **Ignored events in 3b:** `ConflictDetected`, `LeaseWarning`, `Error`, `RemoteNewer`, `Connection` retries. Their facts reach Home through `Status` counts (`conflicts`, `foreign_leases`, `error`), which is all Home needs; the lists and actions are 3c, the timeline is 3d. The decoder skips them without error so a newer daemon's events never break an older app (additive protocol).

- `V-SHELL-1` (Task 3 Step 0; pin check in Task 4): FRB 2.13.0 provides a tokio runtime for `async fn` and `StreamSink` tasks that `tokio::net::UnixStream` can use, or `link` needs its own. Until answered the plan assumes it must own one lazily (the safe case).
- `V-SHELL-2` (3d, Flatpak, [SP11](../../decisions.md#d41-a-flatpak-lemusync-reaches-emulator-folders-through-the-document-portal-2026-11-01)): a sandboxed app reaching `$XDG_RUNTIME_DIR/lemusync/daemon.sock` needs a permission (for example `--filesystem=xdg-run/lemusync`); not measured. 3b ships no Flatpak, so the path is the native one.
- `V-SHELL-3` (Task 10 Step 5): the daemon's `Subscribe` loop only logs on `RecvError::Lagged` and continues (`crates/daemon/src/run.rs`); the app misses those events silently. Whether a UI reading continuously can lag the 256-event buffer ([`EVENT_BUFFER`](../../../crates/engine/src/events.rs)) in practice is not measured. Mitigation already in the plan: snapshot on connect and on app resume.
- `V-SHELL-4` (Task 8): `TransferProgress` has no end marker (`TransferPhase` is `checking`, `uploading`, `downloading`), so "this game is syncing" is derived as "progress seen since the last non-syncing status". Whether a stream finishing before the next `StatusChanged` leaves its card showing syncing too long is not measured.
- `V-SHELL-5` (Task 10 Step 5): `Request::Games` goes through the engine's one-at-a-time queue while `Status` and `Subscribe` are answered at once (D35 text, [`service.rs`](../../../crates/engine/src/service.rs)); how long `Games` waits mid-sync on the maintainer's real library is not measured. The app shows the cached list meanwhile.
- `V-SHELL-6` (Task 8): the Games card shows the emulator's profile id; whether the profile data has a display name the catalog can expose is not checked. If it does, a later wire addition fills it; if not, the id stays.
- `V-SHELL-7` (Task 9, Task 10 Step 5): the GTK runner's single-instance switch raises the existing window on Fedora KDE (Wayland) and X11; Wayland focus rules may only flash the taskbar entry.
- `V-SHELL-8` (Task 6, Task 10 Step 5): Ctrl+1–5 and Ctrl+R do not clash with the desktop environment's global shortcuts on the maintainer's KDE; the `meta` variants (macOS) are untested until a Mac runs the app (D40).
