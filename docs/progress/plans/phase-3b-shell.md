# Phase 3b, app shell and live status

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Also follow the project skills: `lemusync-feature` (always), `lemusync-docs` (every task), `lemusync-ui` (Tasks 6–11), `lemusync-security` (Tasks 3, 4, 5: IPC client, data from the socket).

**Goal:** The LemuSync desktop app opens, finds the running daemon, and shows what it knows: a two-destination shell, Home and Games, that shows only what works (same order everywhere, F3; Activity, Devices and Settings appear in 3d), a Home with the live status hero and the play-session overlay, recent games, and a read-only Games library, all fed by the daemon's event stream through the bridge. Second of the four Phase 3 plans ([roadmap](../roadmap.md#phase-3-flutter-app-desktop), [D40](../../decisions.md#d40-the-desktop-ui-comes-before-the-windows-and-macos-daemon-2026-11-01)). Linux first; the code has no per-OS visual branch.

**Architecture:** The app is a client of `lemusyncd` ([D35](../../decisions.md#d35-the-cli-is-the-daemons-client-while-it-runs-2026-10-28)): Flutter → FRB → `crates/bridge` → `crates/ipc` `Client` → the daemon socket. `lemusync_ipc::Client` already is the shared client (the CLI's `daemon_client.rs` wraps it with CLI-only typing), so nothing moves down a layer and no protocol is added. The bridge gets a `link` module (plain async Rust, tested against a real `lemusync_ipc::Server`) and a thin `api/daemon.rs` FRB surface over bridge-owned DTOs (no serde, no secrets). Calls use one short connection each, every one with a timeout; one long-lived task owns the event subscription (the daemon's `Subscribe` loop never reads requests again, so a subscribed connection cannot also call: `crates/daemon/src/run.rs`) and reconnects with backoff. The task subscribes first, then fetches Status, then Games on its own short connection, so events keep flowing while `Games` waits behind a sync (V-SHELL-5). "Daemon not running" is a value (`ConnectionState`), never an exception. The game-library rule (which games, which streams, in which order, launchable or not, and the recent-play list) is pure code in `lemusync-engine` shared by the tray and the app (`lemusync-api` stays wire types only; `bridge` and `daemon` may both depend on `engine`: `xtask/src/layers.rs`). In Dart, one `AppController` (a `ChangeNotifier`, no new package) holds connection, status, session, library and live transfers, built from the event stream and tested with a fake link. `AppShell` shows the destinations as bottom bar, rail or sidebar by width.

**Tech Stack:** Rust 1.99.0; existing workspace crates `tokio`, `futures-util` (already in `Cargo.lock`, now also `lemusync-bridge` dependencies) plus `lemusync-api`, `lemusync-engine` and `lemusync-ipc` (all allowed for `bridge` by `cargo xtask layers`); `flutter_rust_bridge` Rust `=2.13.0`, Dart `2.13.0`, codegen 2.13.0 (pinned in `app/pubspec.yaml` and `crates/bridge/Cargo.toml`; `flutter_rust_bridge_codegen --version` printed 2.13.0 on 2026-11-01); Flutter 3.47.6. No new Dart or Rust package (router and state use the framework: P1).

**Spec:** [navigation](../../specs/ui/navigation.md) §Destinations, §Adaptive containers, §Deep links, §Desktop extras; [design-system](../../specs/ui/design-system.md) §Components, §Accessibility, §Performance; [status-and-notifications](../../specs/ui/status-and-notifications.md) §Status model, §Desktop tray and menu bar; [architecture](../../specs/architecture.md) §Components, §Engine API, §IPC, §Bridge; [app-shell](../../specs/ui/app-shell.md); [testing](../../specs/testing.md) §Layers, §Rules; [i18n](../../specs/i18n.md) §Terminology. Every bridge call has a timeout (V-SHELL-12) and a cancelled Dart stream stops the Rust task at once (V-SHELL-11). Window close quits the app only; the daemon, the tray and the sync keep running.

The decoder skips them without error so a newer daemon's events never break an older app (additive protocol).
